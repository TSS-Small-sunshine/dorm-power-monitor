## 2. 🔴 阻断级问题（动工前必须解决）

### B1 — armv7 与"保留全部依赖"直接矛盾 ❌

**问题**：`Q3（覆盖所有 Linux 架构）` 与 `Q4（依赖全保留）` 在 **armv7** 上**无法同时成立**。

**实证**：

| 事实 | 证据 |
|---|---|
| `pydantic-core` **无 armv7 wheel** | 上游 issue `pydantic/pydantic#12194`「No prebuilt wheel for ARMv7l」 |
| `bcrypt` 4.x/5.x 是 **Rust** 实现 | `pyca/bcrypt#409`「Precompiled ARM package in pip?」 |
| 方案 §5.1 的 Dockerfile 用 `python:3.12-slim` 作构建基础镜像 | 该镜像**不含 Rust 工具链** |
| → pip 会尝试**源码编译** `pydantic-core` | **必然失败**（`cargo: not found`） |
| 即使加 Rust 工具链，armv7 走 **QEMU 模拟** | Rust 编译极慢（30–60 分钟）+ 512MB 上易 OOM |

**结论**：方案 §5.1 的 Dockerfile 草案**在 armv7 上跑不通**。这不是"风险"，是"必然失败"。

**必须四选一**：

| 选项 | 代价 |
|---|---|
| ① 砍掉 Rust 依赖（pydantic + bcrypt 换 stdlib） | 改动 Q4；但 pydantic 已可选用、bcrypt 可换 `hashlib.scrypt` |
| ② 放弃 armv7（只支持 amd64 + arm64） | 改动 Q3；armv7 用户走"自行编译" |
| ③ 加 Rust 工具链 + 接受 30–60 分钟构建 | 构建复杂、CI 成本高、仍可能失败 |
| ④ armv7 提供"预编译 wheel 缓存"路径 | 需自建 wheel 源，维护成本高 |

### B2 — 生产 Web 服务器选型未决（且现状是 Flask 开发服务器）❌

**问题**：方案假设"gunicorn 单 worker"，但**没有写明这是一个变更**，且现状与假设完全不同。

**实证**：

| 检查项 | 结果 |
|---|---|
| `deploy/dorm-web.service` 的 `ExecStart` | `/opt/dorm-power-monitor/.venv/bin/python /opt/dorm-power-monitor/web.py` |
| `web.py:3101` | `app.run(host=..., port=..., debug=config.FLASK_DEBUG)` ← **Flask 开发服务器** |
| `gunicorn` 在代码/部署/nginx/setup.sh 中的引用 | **0 处**（只在 `requirements.txt` 里躺着） |

**风险**：
1. Flask 开发服务器官方**禁止用于生产**（单线程、无进程管理、有安全告警）
2. `app.run(debug=True)` 会启用 **reloader → fork 两个进程** → 若调度器在模块导入时启动，会**启动两次 → 重复抓取**

**方案缺口**：没有写"改用 gunicorn + 1 worker + systemd unit 改造"，这属于**部署契约变更**，必须显式列出。

---

### B3 — APScheduler 的启动时机未设计 ❌

**问题**：`Q14` 选了"APScheduler 进程内调度"，但**方案完全没有设计它在 Web 服务器生命周期中的启动时机** —— 而这正是该方案最容易崩的地方。

**三种失败场景**：

| 场景 | 后果 |
|---|---|
| 模块导入时 `scheduler.start()` + gunicorn `--preload` | 在 master 启动 → fork 后**线程丢失**，调度器实际不工作 |
| gunicorn 多 worker | **每个 worker 各启动一次** → 重复抓取 N 倍 |
| Flask dev server + reloader（`debug=True`） | 父子进程各启动一次 → **重复抓取** |

**正确做法**（方案缺失）：在 gunicorn 的 `post_fork` hook 中启动，或用 `gunicorn.conf.py` 的 `when_ready`；并显式禁用 `--preload`。

**方案现状**：只有一句"启动时断言单 worker" —— **不够**（断言挡不住 `--preload` 的 fork 场景）。

### B4 — Q19（随机密码）与 OOBE 的接缝未缝合 ❌

**问题**：两个已确认的决定**互相矛盾**。

| 决定 | 内容 |

| **OOBE H1** | 6 步向导，其中**第 6 步是"创建管理员账号（username + password）"** |

**矛盾**：到底是"安装时随机生成"还是"OOBE 时用户自己设"？两套流程都指向同一个 `users` 表。

**必须二选一**：

| ② 安装时随机生成 + OOBE 跳过建号 | OOBE 第 6 步改为"显示随机密码 + 强制改密" |
| ③ 混合：有 `.env` 密码则用，无则随机生成 | 保留两条路，但要写清优先级 |

### M2 — 🔴 明文密码路径未清理（本次审查新发现）

**问题**：`meta.admin_password` **仍在活跃使用**，且**明文存储**。

**实证**：

| 位置 | 行为 |
|---|---|
| `web.py:1240` | `_admin_required` 装饰器读 `meta.admin_password` 做认证 |
| `web.py:2288` | **明文写入** `db.set_meta("admin_password", pwd)` |
| `web.py:2396` | **明文写入**（`/admin/set-password` 恢复入口） |

**与文档矛盾**：`R68_RELEASE_NOTES.md` 声称
> "Pre-R63 HTTP Basic Auth against `meta.admin_password` is **fully removed**; that variable is **no longer read** by `web.py`."

→ **与代码不符**（这是本次发现的**第 4 处**文档/代码不符）。

**必须纳入范围**：删除 `_admin_required` 装饰器 + `meta.admin_password` 的全部读写路径。

### M3 — "容器停机补跑"的收益被夸大

**问题**：方案 §Q14 称 `coalesce=True` + `misfire_grace_time` 能"处理容器停机错过的抓取"。

**事实**：APScheduler 的 misfire 机制只处理 **"scheduler 在运行、但任务被阻塞"** 的情况。**进程不在时不会补跑** —— 重启后只是等下一个 `*/10` 整点。

**影响**：
- 不是功能回归（现有 host cron 也不补跑）
- 但**方案表述误导**，且**验收标准不能按"会补跑"来写**
- 若真需要补跑，要额外设计（启动时检查 `last_scrape_at` 缺口 → 主动补一次）
